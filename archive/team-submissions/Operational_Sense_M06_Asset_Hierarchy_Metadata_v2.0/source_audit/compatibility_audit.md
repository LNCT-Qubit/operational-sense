# M04/M05 compatibility audit

## Findings

1. M04 is logical design v1.1 and not formally approved.
2. M04 proposes `EQUIPMENT_CLASS` and `ASSET_NODE`; it does not supply production PostgreSQL DDL.
3. M04 says M05 owns DDL, migrations, indexes, triggers and production loading scripts.
4. No M05 files were visible in the public repository root listing; direct git remote inspection failed due DNS.
5. Repository README describes Spring Boot, but the task prompt describes Node.js + Express. A migration runner and backend path cannot be inferred safely.
6. The candidate migration uses M04 logical names and intentionally fails if `public.equipment_class` or `public.asset_node` already exists.
7. The candidate uses `BIGINT GENERATED BY DEFAULT AS IDENTITY` for `asset_id`, a provisional implementation choice because M04 Q09 does not specify the identifier strategy.
8. The candidate uses arbitrary-depth parent-child links with cycle protection, but does not constrain level vocabulary or parent/child level combinations because Q01 is open.
9. `m06_equipment_component_reference` is namespaced and provenance-focused to avoid promoting pending source labels to an approved taxonomy entity.

## Status

- Static source mapping: implemented and testable without PostgreSQL.
- Candidate schema/migration: implemented, but not verified against M05.
- PostgreSQL execution: NOT RUN (`psql` and Docker unavailable).
- Live repository integration: BLOCKED (no local checkout; git DNS failure).
- Domain/architecture approval: PENDING REVIEW.
